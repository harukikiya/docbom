# DocBOM 開発ロードマップ

状態：M0・M1・M2完了、M3a実装済み。M3bの差分検査は未実装。最初は対象形式を広げず、小さな縦断プロトタイプを優先する。

## 基本方針

最初に作るのは、大きな文書管理サービスではなく、次をまとめた**DocBOM Starter Kit**である。

- 仕様とデータモデル
- スキーマとテンプレート
- 小さなCLI
- 架空文書による例とテスト
- 実際のプロジェクトへ導入する手順

実際のベンダー文書や職場の実データは、公開するStarter Kitとは別の文書リポジトリで扱う。

## M0：設計土台

完了条件：

- 解決したい問題と非目標を文書化する
- 中央文書リポジトリとプロジェクト側の責務を分ける
- Document、Revision、Artifact、Capture、Derivativeを区別する
- Web再取得のバイト一致を保証しない方針を明確にする
- 最初の未決事項を列挙する

対応文書：

- `README.md`
- `docs/architecture.md`
- `docs/data-model.md`
- 本ファイル

### 架空文書

再配布可能な架空の製品「ACME MCU100」を使い、次を用意する。

- Datasheet Rev. 1とRev. 2
- Reference Manual
- Silicon A1向けErrata
- Web Manualの取得版1と取得版2
- 特定コミットに固定したGit文書（Markdown）
- 旧版に固定するプロジェクト
- 新版を採用するプロジェクト

架空文書では、本文変更、図だけの変更、ページ追加、同じURLでの差し替えを自由に再現できるようにする。

### 完了条件

- 旧版と新版を上書きせず表現できる
- A1向けErrataをA2のプロジェクトへ適用しない
- 版が不明な文書を推測なしで登録できる
- 人が書くYAMLと機械が書く状態を分けられる

## M2：最小CLI

`python -m docbom` として実行する。利用方法は[CLI利用手順](cli.md)を参照。

### init

文書リポジトリとプロジェクト設定の雛形を生成する。

### ingest

- 実体を保存する
- ハッシュを計算する
- Document YAMLの下書きを生成する
- 取得日時を記録する
- 可能な範囲でタイトルや目次を抽出する

初期対応形式はPDF・Webページ・Git文書とする。M2ではPDFとGit文書の取り込みを実装し、Web取得はM3で追加する。CHMなどの追加形式は後続課題とする。

### validate

- スキーマ検証
- IDの重複と関係先の検査
- ファイル存在とハッシュ一致
- 不完全な取得版の誤登録防止

### resolve

プロジェクトの採用条件から文書集合を解決し、`docbom.lock.yaml` を生成する。

### get

ロックされた文書実体のパス取得・複写、PDFのページ指定、Git文書の行範囲指定による本文抜粋を行う。章や高度な出典位置の解析は後続課題とする。

### 完了条件

```text
init → ingest → validate → resolve → get
```

を架空文書セットで通し実行できる。

## M3：Web取得と差分検査

### M3a：静的Web取得の最小実装（実装済み）

- 版管理されたCapture Profileを読み込み、entrypoint・同一オリジン・allowed_paths・除外パターンを適用する
- 静的HTML・CSS・画像を取得し、WARCとURL別資源一覧をハッシュアドレスで保存する
- 取得成功・失敗・除外を `state/` の取得レポートへ記録する
- 失敗を含む取得を部分取得として保存し、成功と混同しない
- 再取得しても既存の取得版・Document YAML・プロジェクトロックを自動変更しない
- 実在サイトへアクセスせず、ローカルの架空Webサイトでテストする

M3aではJavaScriptを実行せず、リダイレクトもたどらない。認証付き取得、ブラウザ自動化、詳細な差分検査はこの段階の対象外とする。

### M3b以降：再取得と差分検査（未実装）

- 同じ取得プロファイルによる二回取得と非決定性の検証
- 前回取得版との比較レポート
- 正規化本文ハッシュの生成
- 必要に応じた固定ブラウザ環境での取得

### ハッシュの使い分け

- 生取得データのハッシュ：その取得イベントの厳密な識別
- URL別資源一覧のハッシュ：取得集合の固定と変化検出
- 正規化本文のハッシュ：比較の補助（M3b以降）

正規化本文の一致だけで、画像や表を含む文書全体が無変更とは判断しない。

### M3全体の完了条件

- 同じ取得プロファイルで二回取得し、差を説明できる
- 取得範囲内の欠落と失敗を報告できる
- 再取得物が既存の取得版を自動置換しない
- 差分が、取得の非決定性・取得漏れ・公式側更新のどれに相当するかを人が確認できる

## M4：二つのプロジェクトで更新運用を検証

### 作るもの

- 中央目録のリビジョンを記録したロックファイル
- 新版候補の登録状態
- ロックファイルからの影響プロジェクト逆引き
- 明示的なロック更新

### 完了条件

- 中央に新版を追加しても旧プロジェクトのロックは変わらない
- 新版を採用するプロジェクトだけが明示的に更新できる
- どのプロジェクトが旧版を使っているかを一覧できる
- 適用対象外のErrataが影響通知の対象から外せる

## M5：AI接続の実証

最初はMCPを作らず、`resolve` と `get` の結果を既存のAIへ渡して検証する。

確認事項：

- ロックされた文書集合以外を参照していないか
- 文書ID、版、実体ハッシュ、出典位置を返せるか
- 旧SDK向けプロジェクトで、新版だけの機能を混ぜないか
- 新しい候補版がある場合に、採用版と区別して報告できるか

その後、必要に応じて次を薄いMCP機能として公開する。

- `resolve_documents`
- `search_locked_documents`
- `get_passage`

## 初期の受け入れ試験

1. 同じロックファイルから常に同じハッシュの文書集合が得られる
2. 同じURLの文書差し替えで旧版を上書きしない
3. 別URLの新版は、ハッシュ不変をもって不存在と判断しない
4. A1向けErrataをA2へ適用しない
5. Web文書の過去の取得版を再取得できる
6. 不完全なWeb取得を完全版として扱わない
7. AIの回答から文書ID、版、実体、位置へ戻れる
8. 中央の新版登録によって既存プロジェクトが黙って変わらない
