# DocBOM 全体設計

状態：v0.1草案。実装前の検討用。

## 1. 目的

DocBOMは、ベンダーなどの外部から提供される技術文書を、版・出所・実体ハッシュ・適用条件付きで管理し、プロジェクトごとに使用文書を確定するための仕組みである。

主な目的は次のとおり。

- 古い版や適用対象外の文書を誤って使うことを防ぐ
- 文書の更新と、その影響を受けるプロジェクトを把握できるようにする
- 過去の設計・検証・AI回答が、どの文書実体に基づいたかを再確認できるようにする
- PDF、Web、CHMなどの異なる提供形式を、共通の版管理と出典管理へ載せる

DocBOMが保証するのは文書内容の正しさではなく、**文書の同一性、取得経緯、選択結果、参照位置の追跡可能性**である。

## 2. 三つの管理領域

```text
DocBOMの公開リポジトリ
  仕様、スキーマ、テンプレート、CLI、架空文書による例とテスト

実際の文書リポジトリ
  外部文書の実体、取得版、目録、派生物、検査記録

各利用プロジェクト
  文書の採用条件と、解決済みのロックファイル
```

実際の文書リポジトリは、個人用と職場用を分ける。アクセス権や守秘義務の境界が異なる場合は、無理に一つへ統合しない。

## 3. 中央文書リポジトリ

```text
docbom-store/
├─ subjects/       チップ・ツール・製品などの適用対象
├─ manifest/       文書系列・版・適用条件・関係
├─ store/
│  ├─ source/      公式配布物。PDF・ZIP・CHM・SDKなど
│  └─ capture/     Web・API・アプリなどからの取得証跡
├─ derived/        展開HTML・OCR・テキスト・文字起こしなど
├─ state/          最終確認・差分検出・取得失敗などの機械的記録
├─ index/          章立て・逆引き・検索索引
└─ reports/        更新・影響・棚卸しレポート
```

### subjects

文書ではなく、文書が適用される対象を管理する。例として、チップとシリコンRev、ツールと製品版、家電の型番や地域がある。

### manifest

人が確認した情報を管理する。原則として一文書系列一ファイルとし、内部に版の一覧を持つ。版によって適用条件や関係が変わる場合は、版ごとの値で上書きできるようにする。

### store/source

ベンダーが配布した原本を加工せず保存する。旧版を上書きせず、ファイルハッシュで特定する。

### store/capture

Web、API、アプリ内ヘルプなど、不変ファイルとして配布されない情報の取得証跡を保存する。これは公式配布物そのものではなく、**公式情報源から自分たちが取得した版**として扱う。

### derivedとindex

原本または取得版から生成する。生成元ハッシュ、生成ツールと版を記録し、原本が変わった古い派生物を使い回さないようにする。再生成可能なため、原本とは別の保存・削除方針を適用できる。

### state

定期検査による差分を人間用の目録へ直接書き込まない。最終確認日時、通信失敗、検出された変化、検査ツールの版などを記録する。

## 4. プロジェクト側の管理

各プロジェクトには、文書実体ではなく次の二ファイルを置く。

### docbom.yaml

人が管理する採用条件。対象ハードウェア、SDKやツールの版、固定する文書版、適用されるエラッタの選び方などを記述する。

### docbom.lock.yaml

解決器が生成し、プロジェクトのGitへコミットする確定結果。文書ID、版、実体ハッシュ、取得版ID、中央目録のリビジョンなどを記録する。

中央リポジトリの「把握している最新版」と、プロジェクトの「採用している版」は別である。中央に新版を登録しても、既存プロジェクトのロックを自動更新しない。

## 5. 文書の識別と派生関係

次の階層で考える。

```text
Subject（適用対象）

Document（文書系列）
  └─ Revision（公式上の文書版。不明な場合もある）
       └─ Source Artifact または Capture（実体）
            └─ Derivative（AI・人が利用する派生物）
```

公式版が不明なWeb文書では、版番号を推測で作らず、取得日時と取得版ハッシュで特定する。

## 6. Web取得の再現性

動的なWebでは、取得者や手順を統一しても、再取得のバイト一致を保証できない。DocBOMでは保証対象を次のように分ける。

- 保存済み取得版は不変であり、いつ誰が参照しても同じ
- 再取得物は、取得条件・範囲・失敗・差分を比較できる
- 完全性は、宣言した取得範囲内での完全性として表現する

取得は個人のブラウザ操作ではなく、版管理された取得プロファイルと共通実行環境で行う。開始URL、許可範囲、言語、ブラウザやツールの版、対話操作、失敗時の扱いを記録する。

取得物の厳密な識別には生データのハッシュを使い、再取得物との比較には、URL別資源一覧、正規化本文、画像や表の差分を併用する。正規化テキストが同じでも、文書全体が無変更とは断定しない。

再取得物は既存版を自動置換せず、比較と確認を経て採用する。

## 7. 更新と影響分析

```text
変化の検出
  → 新しい候補版として保存
  → 完全性と差分を検査
  → 人が内容・版・適用条件を確認
  → 中央目録で利用可能にする
  → ロックファイルから影響プロジェクトを逆引き
  → 各プロジェクトが明示的に採用判断
```

同じURLの差し替えだけでなく、別URLで公開される新版を発見するため、製品ページの文書一覧、ベンダー通知、人による定期確認も対象とする。

URLの到達不能と文書の廃止は区別する。

## 8. AI接続

通常の流れは次のとおり。

```text
プロジェクトのロックファイル
  → 使用を許可された文書集合を確定
  → その集合内だけで検索・直接読解
  → 本文と出典位置を取得
  → 文書ID・版・実体・位置を添えて回答
```

AIに全版から最終選択させない。版と適用条件はプログラムが確定し、AIは確定した文書集合の中で検索と読解を行う。

出典位置は形式に応じて、PDFページ、HTMLアンカー、CHM内部パス、Gitコミットとパス、構造化データのレコードID、動画の時間範囲などを使う。

MCPは、これらの機能が安定した後に追加する薄い接続層とする。

## 9. アクセスと公開範囲

次を一つの区分で表現しない。

- 入手時のアクセス条件
- 機密区分
- 再配布可否
- 外部AIへの送信可否

公開リポジトリには、実際のベンダー文書や職場の実データを置かない。公開資料であっても再配布可否を確認し、例とテストには架空または再配布可能な文書を使う。

## 10. 初期の非目標

- 全文書形式の高精度な解析
- Web再取得のバイト一致保証
- 文書内容の正しさや最新性の自動保証
- 既存のQMS、文書管理、PLMの置き換え
- 最初からのGUI、データベース、大規模RAG基盤
- 公開文書の無条件な再配布
